综合结论：这次不是单纯“数据集坏了”，而是两类问题叠加：

  1. 点云暴增主要是增密、初始化和裁剪机制的问题。
  2. 点云/几何失败主要是动态场景缺少同一时刻的多视角约束。
  3. V2 数据文件和相机转换基本正确，但采集方式对动态三维恢复仍然不够，且场景尺度与随机点初始化范围不匹配。

  ## 1. 为什么点云暴增

  实际点数变化：

  - 初始化：100,000 个随机点。
  - iteration 1000：71,895。
  - iteration 5000：184,356。
  - 5000 后冻结增密，因此最终仍为184,356。
  - 6060 左右没有保存 point checkpoint，无法给出当时准确点数，但显存从约11 GB升至17.8 GB、速度从约8 it/s降至2.5 it/s，说明继续增
    密时仍在快速增长。

  主要原因是下面这条链路：

  随机点覆盖范围不足
  + 前1000步形变网络关闭
  + 动态物体和相机同时运动
          ↓
  大量持续的屏幕空间梯度
          ↓
  每100步 clone/split
          ↓
  复制点继承高 opacity
          ↓
  低 opacity pruning 无法抵消新增点
          ↓
  没有点数上限，也没有有效的大 scale pruning

  具体证据：

  - reader 自动生成的随机点只在 [-1.3, 1.3]^3：scene/dataset_readers.py:285。
  - 但布料物体原点位于 z=2.55，初始布料已经在随机点范围之外。
  - 前1000步 d_xyz/d_scaling 等形变全部关闭，但 densification 从500步就开始。这意味着500–999步模型被迫用静态 Gaussian 同时解释所
    有布料位置。

  - iteration 5000 时 opacity 中位数已经达到0.622，约43%的点 opacity > 0.99。新 clone/split 会继承这些高 opacity，因此
    min_opacity=0.005 很难删掉它们。

  - max_point_num=150000 虽然出现在函数参数里，但实际上没有执行点数限制。
  - 大点裁剪只有 max_screen_size 生效时才运行；当前 opacity_reset_interval=100000 导致训练期间该分支始终不启用：scene/
    gaussian_model.py:594。

  所以，相机运动弱只能解释几何约束不足，不能单独解释点数暴增。点数暴增的直接原因是“持续高梯度 + 高频增密 + 没有点数/尺度保护 +
  高 opacity 点无法被删”。

  ## 2. 为什么最终点云看不出物体形状

  这里分为“查看方式”和“模型确实训练失败”两部分。

  首先，point_cloud.ply 保存的是 canonical Gaussian，不是某一帧形变后的点云。真正的帧几何还依赖：

  - deform/iteration_35000/deform.pth
  - 当前 timestep
  - 相机中心
  - MLP 输出的 d_xyz/d_rotation/d_scaling/d_opacity

  因此只打开 point_cloud.ply，本来就不能完整看到某一帧的物体形状。普通点云查看器还会忽略 Gaussian 的 scale、rotation、opacity 和
  deformation。

  但本次不只是查看方式问题，模型本身也确实退化了：

  - 最终56.3%的点 opacity < 0.005，属于本应被清理的“死点”；直接查看 PLY 时它们仍会显示并遮蔽结构。
  - 最大 Gaussian scale 的变化为：
      - iteration 5000：2.76
      - iteration 10000：13.13
      - iteration 20000：50.02
      - iteration 30000：111.65
      - iteration 35000：128.46

  - 这说明冻结点数后，优化器继续通过放大少量 Gaussian 来覆盖难以解释的区域，最终形成 alpha 条带和漂浮伪影。
  - 动态点比例最终只有13.7%，明显低于成功 hook 基线的33.9%。
  - 随机初始化点没有使用源 albedo、normal 或真实表面位置；这些输入并没有变成几何监督。
  - 5000步恢复训练只加载了 PLY 和 deform 权重，没有恢复 Adam optimizer state。这不是暴增的根因，但可能加剧后续 opacity/scale 漂
    移。

  最终渲染也证明不是单纯“PLY 看法不对”：椅子和底座能恢复，但红布基本消失，output/Baseline/0716-only_clothV2-stage1/eval/
  eval_gt_left_render_right.png 和 output/Baseline/0716-only_clothV2-stage1/eval/eval_render_alpha_iter35000.png 都显示了实际退
  化。

  另外，最终 PSNR 23.44 不能说明几何正确：

  - 黑背景约占75%–82%。
  - 红布只占约2.5%–7.3%的像素。
  - 当前评估代码最多只检查前4个 test camera，即帧8、16、24、32，没有覆盖布料后期完全落下的状态。
  - 因此“背景、椅子和底座正确，布料缺失”仍可得到看似不低的 PSNR/SSIM。

  ### 采集设计层面：约束不足

  V2 相机全程并不是完全不动：

  - 相机中心跨度：[3.397, 0.055, 0.315]
  - 总视线旋转：23.7°
  - 相机到场景中心距离：约7.98
  - 最大基线/距离：0.427
  - 成功 hook 数据约为1.384

  问题在于 V2 几乎只有沿 X 方向的一维横移，Y/Z 变化很小。更关键的是：

  > 每一个布料时刻只对应一个相机位置，没有同一布料形状下的多个视角。

  相邻帧虽然形状接近，但相机横向位移中位数只有0.025、旋转只有0.19°，局部视差很弱；等相机积累到足够大的基线时，布料形状又已经发生
  明显变化。模型无法明确判断图像变化来自：

  - 相机运动；
  - 布料形变；
  - 深度差；
  - Gaussian 自身的 scale/opacity 变化。

  这就是典型的 camera-motion / object-motion 混淆。

  ### 放慢布料速度为什么仍没解决

  - 原版最大相邻质心位移约17.09 px。
  - V2 最大相邻质心位移降到5.85 px。

  说明 V2 确实消除了剧烈跳变。

  但同时：

  - 原版只有约26.9%的相邻帧移动超过1 px。
  - V2 有约63.0%的相邻帧移动超过1 px。

  也就是说，V2 从“短时间快速掉落、后面长期稳定”变成了“较慢但几乎贯穿整个序列的持续运动”。峰值速度降低了，但有运动的帧更多。对于
  前1000步关闭 deformation、500步就开始 densification 的训练设置，持续运动仍会制造大范围梯度，甚至可能让更多时间段参与错误增密。

  ## 最终判断

  - 数据是否损坏：没有发现损坏。
  - 数据是否足以可靠恢复动态三维：目前不足。
  - 点数暴增的首要责任：训练增密/裁剪机制和随机初始化范围，不是相机移动轻微本身。
  - 点云没形状的首要责任：canonical PLY查看方式、随机体积初始化、死点/巨大 Gaussian，以及“一时刻一视角”的动态几何欠约束。
  - 放慢动态是否有帮助：降低了单步难度，但没有解决相机和物体运动耦合，也让运动覆盖了更多帧。

  最有判别力的下一步不是继续单纯放慢，而是做一个控制数据集：固定一个布料状态，渲染5–8个明显不同的相机视角。如果这个静态多视角版
  本仍恢复失败，重点就是场景归一化和初始化；如果它能恢复，基本可以确认当前失败核心是“每个动态时刻只有一个弱基线视角”。
