## 技术结论

当前不存在“Gaussian 123 对应 Blender 点 123”的一对一 normal 匹配。实际路径是：

    Gaussian 的位置、旋转、尺度、opacity
                    ↓
            当前帧相机投影到屏幕
                    ↓
       Gaussian footprint 覆盖一组像素
                    ↓
      按深度顺序用 alpha/transmittance 合成
                    ↓
          得到像素级 Gaussian normal
                    ↓
       与同一像素的 Blender GT normal 比较

因此当前指标是图像空间的 rasterized Gaussian normal 误差，不是逐 Gaussian 中心点的 3D normal 误差。

当前 world-space 对 world-space 的有效评估结果：

| 指标 | 结果 |
|---|---:|
| 帧数 | 120 |
| alpha 阈值 | 0.5 |
| 平均有效像素 | 46,632.425 / 帧 |
| Mean angular error | 43.7646° |
| Median angular error | 48.1580° |
| P95 angular error | 72.8836° |

结果文件：[normal_metrics.json](/home/han.li/reproduce/LumiMotion-perlight/output/0811-only_clothV3-lambertian-modify/lambertian-modify_mlp/normal_gt_eval/ours_35000_world_audit/normal_metrics.json)。

这个 43.7646° 不能解释为“每个 Gaussian 与 GT 点法线的误差”。它表示经过 Gaussian rasterizer 合成后的像素法线与 Blender 像素法线之间的误差。

## 2. Gaussian normal 的真实来源

### 2.1 初始点云法线没有被继承

points3d.ply 虽然有 nx、ny、nz 字段，但 Gaussian 初始化只读取点位置和颜色，然后把 rotation 初始化为单位 quaternion：

    fused_point_cloud = pcd.points
    fused_color = pcd.colors
    rots[:, 0] = 1

实现位置：[gaussian_model.py](/home/han.li/reproduce/LumiMotion-perlight/scene/gaussian_model.py:266)。

因此初始点云中的 pcd.normals 没有作为训练 normal 监督，也没有直接初始化 Gaussian normal。

### 2.2 训练后的 Gaussian normal 来自 quaternion 的 local +Z

每帧渲染时，Gaussian rotation 会叠加 deformation 的 d_rotation，然后从 rotation matrix 取 local +Z：

    n_raw = normalize(R(q_deformed) · [0, 0, 1])

实现位置：[photometric_lambertian.py](/home/han.li/reproduce/LumiMotion-perlight/scene/photometric_lambertian.py:92)。

这个 n_raw 是 Gaussian 椭圆切平面的法线候选，坐标系是 world-space。

### 2.3 Lambertian 使用 camera-facing 版本

当前渲染器又根据 Gaussian 中心和相机中心翻转 normal：

    s = sign(n_raw · (camera_center - gaussian_position))
    n_photo = s · n_raw

实现位置：[gaussian_renderer/__init__.py](/home/han.li/reproduce/LumiMotion-perlight/gaussian_renderer/__init__.py:139)。

Lambertian 使用的是 n_photo：

    surface_to_light = -ray_dir
    shading = max(0, n_photo · surface_to_light)

所以当前“物理 normal”严格来说是相机朝向的 world-space Gaussian normal，不是跨视角固定的 outward surface normal。

### 2.4 输出 PLY 的 normal 字段不能用于审计

save_ply() 中显式执行：

    normals = np.zeros_like(xyz)

因此训练输出的 point_cloud.ply 中 nx、ny、nz 全部为零。真正的 Gaussian normal 必须从 rot_0、rot_1、rot_2、rot_3 重新计算。

证据：[gaussian_model.py](/home/han.li/reproduce/LumiMotion-perlight/scene/gaussian_model.py:384)。

## 3. Gaussian 如何匹配到图像像素

### 3.1 进入 rasterizer 的几何量

渲染入口将以下数据交给 Gaussian rasterizer：

    means3D   = pc.get_xyz + d_xyz
    rotations = pc.get_rotation_bias(d_rotation)
    scales    = pc.get_scaling + d_scaling
    opacity   = pc.get_opacity + d_opacity
    viewmatrix = viewpoint_camera.world_view_transform
    projmatrix = viewpoint_camera.full_proj_transform

代码位置：[gaussian_renderer/__init__.py](/home/han.li/reproduce/LumiMotion-perlight/gaussian_renderer/__init__.py:76)。

这意味着 Gaussian 的位置和形状先经过当前帧 deformation，再使用当前帧 camera 投影。GT normal 并没有参与这一步匹配。

### 3.2 rasterizer 内部的 Gaussian normal

CUDA rasterizer 对每个 Gaussian 使用 quaternion 的第三列作为切平面法线：

    R  = quat_to_rotmat(quat) * scale_to_mat(...)
    tn = W * R[2]

W 将 world normal 转到 runtime view-space。随后 rasterizer 根据观察方向进行 camera-facing 翻转：

    cos = dot(-tn, p_view)
    if cos <= 0:
        tn *= -1

代码位置：[forward.cu](/home/han.li/reproduce/LumiMotion-perlight/submodules/2dgs_rasterizer_lumimotion/diff-surfel-rasterization/cuda_rasterizer/forward.cu:83)。

这个方向规则与 Python 中 orient_normal_toward_camera() 的目标一致。Lambertian 使用的 Gaussian normal 和 rasterizer normal map 的法线来源是同一组 deformation 后 quaternion。

### 3.3 一个像素可能对应多个 Gaussian

对像素 p，rasterizer 计算每个 Gaussian 的局部 footprint：

    rho3d / rho2d → rho → power → alpha

然后计算：

    alpha_i(p) = min(0.99, opacity_i · exp(power_i(p)))
    T_i(p)     = Π(j<i) (1 - alpha_j(p))

Gaussian 按深度排序累积，像素 normal 为：

    N_raw_pixel(p) = Σ_i [alpha_i(p) · T_i(p) · n_i(p)]
    N_gs(p)        = normalize(N_raw_pixel(p))

CUDA 累积位置：[forward.cu](/home/han.li/reproduce/LumiMotion-perlight/submodules/2dgs_rasterizer_lumimotion/diff-surfel-rasterization/cuda_rasterizer/forward.cu:390)。

当前 Python 端没有先除以 alpha，而是在评估时对合成后的 rend_normal 单位化。因此它衡量的是 alpha-weighted blended normal 的方向。

## 4. GT normal 如何与 Gaussian normal 对齐

评估器对每个 camera record 执行：

1. 根据 source_frame 找到对应的 normal_XXXX.exr；
2. 使用 OpenEXR 读取 Normal.X/Y/Z；
3. 将 EXR normal resize 到当前 render 分辨率；
4. 对 GT normal 单位化；
5. 使用 rend_alpha >= 0.5 和 GT normal 有效性生成 mask；
6. 将 renderer 的 rend_normal 转回 world-space 并单位化；
7. 在相同图像像素上计算 angular error。

实现位置：

- GT 读取与单位化：[eval_stage1_normals_gt.py](/home/han.li/reproduce/LumiMotion-perlight/scripts/eval_stage1_normals_gt.py:52)
- alpha 前景筛选：[eval_stage1_normals_gt.py](/home/han.li/reproduce/LumiMotion-perlight/scripts/eval_stage1_normals_gt.py:146)
- world normal 对比：[eval_stage1_normals_gt.py](/home/han.li/reproduce/LumiMotion-perlight/scripts/eval_stage1_normals_gt.py:140)

数学定义：

    theta(p) = acos(clamp(normalize(N_gs(p)) · normalize(N_gt(p)), -1, 1))

这个流程是像素对像素，而不是 Gaussian ID 对 GT 点 ID。

## 5. 训练阶段是否使用了 GT normal

没有。训练阶段 normal loss 的输入是：

    rend_normal = rasterized Gaussian normal
    surf_normal = depth_to_normal(rendered_depth)

训练损失为：

    L_normal = lambda_normal · mean(1 - rend_normal · surf_normal)

代码位置：[train_stage1.py](/home/han.li/reproduce/LumiMotion-perlight/scripts/train_stage1.py:568)。

surf_normal 来自渲染深度的邻域差分，不是 Blender normal_exr。因此 Gaussian rotation 是通过 RGB/Lambertian 重建、几何梯度和 depth-derived normal regularization 间接学习的。

GT normal EXR 只在事后评估脚本中读取，不是训练监督。

## 6. 当前 43.76°指标的准确含义

当前结果：

    Mean   = 43.7646°
    Median = 48.1580°
    P95    = 72.8836°

它表示：对 120 帧中 alpha >= 0.5 的前景像素，比较 rasterizer 合成的 world-space Gaussian normal 与 Blender world-space normal pass 的夹角。

它不表示：

- 每个 Gaussian 中心点与 Blender 网格点的误差；
- PLY 中 nx、ny、nz 与 GT 的误差；
- Gaussian 原始 n_raw 与 GT 的误差；
- 训练时直接使用 GT normal 后得到的误差。

历史的 126.805°结果来自旧评估 JSON，其中把 world-space EXR 额外当成 camera-space 做了 Y/Z 转换，不能继续使用。历史文档中的 normal-depth 17°–22°也不是 GT normal angular error，不能与本报告的 43.76°直接比较。

## 7. 当前路径的主要限制

### 7.1 没有逐 Gaussian 的 GT 对应记录

当前输出没有保存：

    frame_id
    gaussian_id
    projected_u
    projected_v
    depth
    visibility
    alpha contribution
    n_raw
    n_camera_facing
    GT normal sampled at projected location

因此目前不能回答“某一个 Gaussian 的 normal 与哪个 GT surface point 对应”。

### 7.2 alpha 混合会隐藏单个 Gaussian 的误差

一个像素可能由多个 Gaussian 覆盖。一个错误 Gaussian 可能被前景 Gaussian 遮盖，也可能通过加权平均产生看似合理的像素 normal。

像素级误差适合评估最终渲染质量，但不适合诊断单个 Gaussian 的几何法线。

### 7.3 camera-facing 不是固定 physical outward normal

当前 normal 会根据相机方向翻转。V3 清单确认有 120 个不同 camera matrix，因此同一个 Gaussian 的法线符号可能随相机改变。

这对当前可见视角渲染是合理的，但对跨视角、跨光源的物理 relighting 不够严格。至少还应报告 sign-invariant 误差：

    theta_abs(p) = acos(abs(normalize(N_gs(p)) · normalize(N_gt(p))))

## 8. 建议新增的逐 Gaussian 审计路径

为了真正回答“Gaussian normal 对应哪个 GT normal”，建议新增独立诊断，不替代当前像素评估。

### 8.1 计算每帧 Gaussian 属性

    x_i^t       = xyz_i + d_xyz_i^t
    q_i^t       = rotation_i + d_rotation_i^t
    n_raw_i^t   = normalize(R(q_i^t) · +Z)
    n_face_i^t  = orient_to_camera(n_raw_i^t, x_i^t, camera_center_t)

### 8.2 使用同一个 camera 投影 Gaussian 中心

使用 renderer 当前的 world_view_transform 和 full_proj_transform 得到：

    (u_i^t, v_i^t, depth_i^t)

不能使用另一套 Blender/OpenGL 投影实现，否则会引入新的坐标系误差。

### 8.3 采样 GT normal

在 GT EXR 的 projected pixel 处双线性采样：

    n_gt_sample_i^t = bilinear_sample(N_gt^t, u_i^t, v_i^t)

同时使用：

- Gaussian 是否在视锥内；
- projected depth；
- rasterizer visibility；
- Gaussian 对该像素的 alpha contribution；
- alpha mask。

### 8.4 输出 Gaussian 级指标

有符号误差：

    acos(n_face_i · n_gt_sample_i)

符号不变误差：

    acos(abs(n_raw_i · n_gt_sample_i))

建议输出：

    gaussian_normal_audit.jsonl
    gaussian_normal_error_histogram.png
    gaussian_normal_3d.ply
    gaussian_normal_projection_contact_sheet.png

gaussian_normal_3d.ply 必须将计算出的 normal 写入真正的 nx、ny、nz，不能复用当前 save_ply() 的零占位字段。

### 8.5 同时保留四类指标

| 指标 | 回答的问题 |
|---|---|
| 像素级 raster normal error | 最终渲染出来的 normal image 是否正确？ |
| Gaussian 投影采样 error | 单个 Gaussian 的 normal 是否接近对应 GT surface normal？ |
| sign-invariant error | 是否只是 2DGS normal 正负符号歧义？ |
| front-most-only error | 最前面可见 Gaussian 是否正确？ |

不能用其中一个指标替代另外三个。

## 9. 最终判定

### 已确认正确

- Gaussian normal 的真正来源是 deformation 后 quaternion 的 local +Z，不是 PLY normal 字段；
- Lambertian 和 rasterizer 使用同一批 deformation 后 Gaussian rotation；
- 当前 GT EXR 是 world-space；
- 当前 evaluator 已改为 world-space 对 world-space；
- 当前 43.76°是有效的像素级 normal 误差；
- alpha mask 被用于前景筛选。

### 尚未完成

- 没有 Gaussian 中心到 GT surface point 的一对一匹配；
- 没有保存每个 Gaussian 的投影坐标、可见性和 GT sampled normal；
- 没有单独报告 n_raw、n_camera_facing 和 sign-invariant 三种 Gaussian 级误差；
- 当前 PLY normal 字段不能用于法线审计。

因此本实验当前可以得出：

> 0811-only_clothV3-lambertian-modify 的最终 rasterized Gaussian normal 与 Blender GT normal 的 world-space 像素误差约为 43.76°；但还不能据此声称每个 Gaussian 的 physical normal 已经与 Blender 表面点 normal 正确对应。

下一步应先实现逐 Gaussian 投影、可见性筛选和 GT normal 采样，再决定是否修改训练中的 normal supervision。
