## 2. 总结

用户关于 per-light normal 弱于原始 LumiMotion baseline 的判断成立。

固定视角下，baseline raster normal 与 depth-derived surface normal 的平均夹角为
`17.28°–22.11°`，per-light 为 `42.00°–43.80°`。per-light 的相邻像素
normal 变化反而更小，说明其主要问题不是随机噪声，而是 normal 更平滑、更趋同，
但方向和局部结构不准确。这与 contact sheet 中 per-light normal 偏紫、几何方向
变化减弱的现象一致。

没有发现 photometric shader 把 camera-space normal 与 world-space light 直接做
点积，也没有发现本数据路径混用了 Blender、COLMAP 或 OpenGL 相机轴。

本次检查发现的关键问题是：

> Per-light shader 直接使用 Gaussian quaternion 的未定向 local `+z`；
> rasterizer 与 normal regularizer 则会把同一个 normal 翻转到朝向当前相机的一侧。

对于发生翻转的 Gaussian，photometric RGB loss 和 raster normal regularizer
实际使用相反方向的 normal。35k per-light checkpoint 的三个代表帧中，有
`11.50%–14.46%` 的 Gaussian 发生这种 180° 翻转；按 opacity 加权后为
`3.88%–7.18%`。

此外，最终 learned light 与 `lights.json` 中真实 Blender world-space
light-to-scene ray 的平均夹角约为 `35.40°`，说明 learned light、normal 和
albedo 之间仍有明显分解歧义。

## 3. Normal 是 camera-space 还是 world-space

代码中存在两条不同的 normal 路径。

### 3.1 Per-light shader normal

`scene/photometric_lambertian.py::get_gaussian_normal` 从 Gaussian quaternion
构造 rotation matrix，然后选择 local `+z`：

```python
axis = parse_axis(normal_axis, rotation_matrix.device)
normal = F.normalize(
    torch.matmul(rotation_matrix, axis.view(3, 1)).squeeze(-1),
    dim=-1,
)
```

这里没有乘 world-to-camera rotation，因此输出是 world-space normal。

本实验 checkpoint 配置为：

```text
normal_axis = +z
direction_convention = light_to_surface
```

Local `+z` 与 2D Gaussian 的法向轴一致：CUDA rasterizer 同样使用 rotation
matrix 的第三列 `R[2]` 作为 tangent plane normal。

### 3.2 Contact sheet normal

Rasterizer 首先在 camera/view space 计算：

```cpp
glm::vec3 tn = W * R[2];
```

随后 `allmap[2:5]` 返回 alpha-weighted view-space normal accumulation。

Python 端同时产生两个输出：

```python
render_normal = allmap[2:5]
render_normal = render_normal @ world_view_rotation.T

render_normal_view = -allmap[2:5]
```

- `rend_normal`：转换回 world space，用于 normal regularization。
- `rend_normal_view`：取负后的 view-space normal，用于 Stage 1 insights。

`render_stage1_insights.py` 保存 contact sheet 时使用的是：

```python
norm_rend = render_pkg["rend_normal_view"] * 0.5 + 0.5
```

所以用户比较的两张 normal contact sheet 都是取负后的 camera/view-space normal，
不是 per-light shader 中直接参与 `n·l` 的 world-space normal。

两张图使用同一种可视化定义，因此二者的差异不是 world-space 与 camera-space
展示方式不同导致的；它反映了训练后 Gaussian rotation/geometry 的真实差异。

## 4. Light direction 是 camera-space 还是 world-space

Per-light 的 light table 是 world-space。

实验使用的 camera-back ellipse 初始化依据为：

- camera center ray 转换后的 world-space forward；
- world-space camera right；
- world-space camera up。

初始化得到的向量以及随后自由学习的每帧向量均没有乘 world-to-camera rotation。
Checkpoint 的保存约定为：

```text
light_to_surface
```

也就是向量代表光传播方向：从光源指向场景表面。

原始 `lights.json` 中的 `light_pos_world` 同样是 Blender world-space position。
本次比较 learned light 与真实光向时使用：

```text
normalize(scene_centroid_world - light_pos_world)
```

没有进行 camera-space 变换。

## 5. 渲染时 normal 与 light 是否在相同坐标系

是。Photometric renderer 中：

```python
normal = F.normalize(normal, dim=-1)
ray_dir = F.normalize(ray_dir, dim=-1)
surface_to_light_dir = -ray_dir
ndotl = (normal * surface_to_light_dir[None]).sum(dim=-1, keepdim=True)
shading = ndotl.clamp_min(0.0)
```

这里的 `normal` 和 `surface_to_light_dir` 都是 world-space。

所以没有出现以下错误：

```text
camera-space normal · world-space light
```

但存在另一种不一致：shader normal 没有采用 rasterizer 的 camera-facing
定向规则。也就是说两者的坐标基相同，但 normal 的正负面定义不相同。

## 6. Normal 是否经过归一化

### 6.1 Per-Gaussian photometric normal

已经归一化两次：

1. `get_gaussian_normal` 返回前进行 `F.normalize`；
2. `PhotometricLambertianRenderer.forward` 点积前再次进行 `F.normalize`。

Checkpoint 数值检查中，三个代表帧的 per-Gaussian normal：

```text
mean norm = 1.0
max |norm - 1| <= 3.58e-7
```

### 6.2 Light direction

Light table 每次读取时进行 `F.normalize`，shader 点积前再次归一化。

检查结果：

```text
stored learned ray norm = 1.0
```

### 6.3 Rasterized normal map

Rasterized normal map没有在输出前逐像素归一化。它是：

```text
sum_i(alpha_i * transmittance_i * normal_i)
```

因此其长度同时受到 alpha、overlap 和 Gaussian normal 一致性的影响。
`rend_normal_view * 0.5 + 0.5` 的 contact sheet 也没有先除以 accumulated
alpha 或重新归一化。

训练中的 normal loss 同样直接使用未逐像素归一化的：

```python
normal_error = 1 - (rend_normal * surf_normal).sum(dim=0)
```

其中 `surf_normal` 也乘了 render alpha。这是 baseline 原有行为，并非 per-light
新增，但会让 normal loss 的大小受到 alpha 影响。它也意味着当前 contact sheet
的颜色饱和度不能直接等价为单位 normal 分量。

## 7. Normal 方向翻转

CUDA rasterizer 明确执行双面 camera-facing 翻转：

```cpp
glm::vec3 tn = W * R[2];
float cos = glm::dot(-tn, p_view);
float multiplier = cos > 0 ? 1 : -1;
tn *= multiplier;
```

该规则保证输出 normal 朝向当前相机。

Per-light shader 只执行：

```python
normal_i_t = get_gaussian_normal(normal_rotations, "+z")
```

没有使用 Gaussian position 和 camera center，没有执行相同翻转。

2D Gaussian tangent plane 的 normal 正负本身具有符号歧义：把 tangent basis
的某一方向取反，不会改变表示的平面，但会改变 Lambertian `n·l` 的符号。
原始 rasterizer 通过 camera-facing 规则消除了该符号歧义；per-light shader
重新暴露了它。

35k checkpoint 检查结果：

| Timestep | Baseline 翻转比例 | Per-light 翻转比例 | Per-light opacity-weighted |
| ---: | ---: | ---: | ---: |
| 0 | 10.42% | 14.46% | 4.83% |
| 59 | 5.71% | 11.50% | 3.88% |
| 119 | 5.18% | 12.07% | 7.18% |

这里的翻转比例统计所有 Gaussian；方向判定使用与对应 timestep 相同的原始移动
camera。由于翻转会把 `n·l` 变成 `-(n·l)`，这些 Gaussian 在 raw-normal shader
与 camera-facing shader 中的 lit/unlit 状态也发生改变。

这会造成直接的梯度冲突：

- RGB photometric loss 优化未翻转的 local `+z`；
- raster normal regularizer 优化 camera-facing normal；
- 对发生翻转的 Gaussian，两条路径对应相反的 normal 方向。

## 8. `max(0, n·l)` 中方向定义是否一致

当前代码和本实验 checkpoint 的方向定义一致。

Checkpoint 保存：

```text
ray_dir = light_to_surface
```

Shader 中：

```python
surface_to_light_dir = -ray_dir
ndotl = dot(normal, surface_to_light_dir)
shading = max(0, ndotl)
```

所以 `l` 是从 surface 指向 light 的入射光方向，符合 Lambertian 定义。

本次专门测试了反向情况：

- plane normal：`n=(0,0,+1)`
- 光位于平面上方
- 光传播 ray（light-to-surface）：`(0,0,-1)`
- shader 使用的 surface-to-light：`(0,0,+1)`
- 输出亮度：`1.0`

如果错误地直接用 stored ray 做 `n·l`，该 case 会输出 0；实际没有发生。

## 9. Blender、OpenGL、COLMAP 相机轴检查

源数据 `camera.json` 明确记录 Blender camera convention：

```text
local +X = right
local +Y = up
local -Z = forward
```

`dataset_readers.py` 对 Blender camera-to-world 做标准转换：

```python
matrix = inverse(transform_matrix)
R = -transpose(matrix[:3, :3])
R[:, 0] = -R[:, 0]
T = -matrix[:3, 3]
```

内部 Camera ray 使用：

```text
+X = right
+Y = down
+Z = forward
```

中心 ray 与源 Blender `-Z` forward 的最大分量误差为 `2.76e-8`；相机中心转换
误差为 `6.68e-7`；world normal 经 world → view → world round-trip 的最大误差
为 `1.11e-16`；转换后的 rotation determinant 为 `0.9999999`，仍为右手系。

本数据通过 `transforms_train.json` / `transforms_test.json` 的 Blender reader
加载，没有进入 COLMAP reader。因此本实验没有把 COLMAP camera convention
混入 Stage 1 per-light 路径。

仓库中 PBR normal-map 代码存在 OpenGL/DirectX normal-map convention 开关，但
Stage 1 per-light Lambertian 没有调用该路径。因此 OpenGL normal-map 的 Y 轴
约定不是本次 normal 退化原因。

当前模型同时自由学习：

- 每帧 light direction；
- Gaussian rotation / normal；
- deformation rotation；
- per-Gaussian photometric albedo。

单帧 RGB 对这些变量的约束存在较强歧义。模型可以通过让 normal 更朝向 learned
light、同时调整 albedo，获得较高 PSNR，但不保证几何 normal 正确。Per-light
35k 虽然 PSNR/SSIM 较高，normal-depth angle 和目检均显示几何方向已经退化。

## 13. 建议修复顺序

### 13.1 首先统一 normal 定向规则

在 per-light shader 计算 `n·l` 前，使用 deformed Gaussian position 和当前
camera center，执行与 rasterizer 相同的 camera-facing orientation：

```python
viewdir = means3D - camera_center
normal, _ = flip_align_view(normal, viewdir)
```

然后保证以下三个位置使用同一定向后的 normal：

1. Per-light Lambertian shading；
2. photometric debug 输出；
3. raster normal regularizer 对照统计。

这是最小范围、最接近当前 2DGS 双面语义的修复。

不建议直接把 local axis 从 `+z` 全局改成 `-z`：这只会交换发生问题的
Gaussian 集合，不能消除 2D tangent plane 的符号歧义。

也可以测试 `abs(n·l)` 作为薄布双面材质 ablation，但它会让实体椅子和底座也
变成双面受光，物理含义弱于 camera-facing 一致方案，不应直接替代 baseline。

### 13.2 增加统一 normal debug 输出

建议每个代表帧输出：

- raw world-space local `+z` normal；
- camera-facing world-space normal；
- rasterizer view-space normal；
- rasterizer world-space normal；
- surface-to-light world-space vector；
- raw `n·l`；
- oriented `n·l`；
- normal flip mask。

这样可以直接确认 shader 和 rasterizer 对同一 Gaussian 使用的方向是否一致。

### 13.3 对 normal map 评估使用单位向量

正式 eval 可额外输出：

```python
normal = rend_normal / alpha.clamp_min(eps)
normal = F.normalize(normal, dim=0)
```

并在 foreground mask 内统计 normal-depth angle。保留现有原始
alpha-weighted normal 图，以免改变 baseline 复现路径；新的 normalized normal
图使用不同文件名，作为附加诊断产物。

如果要修改训练 normal loss，也应作为独立 ablation，因为逐像素归一化会改变
baseline loss 的尺度和梯度。

### 13.4 限制 light/normal/albedo 分解歧义

LH Dynamic 已提供真实 `lights.json`。建议优先做以下对照：

1. 固定真实 world-space light direction，只学习 geometry 和 albedo；
2. 用真实 light 初始化，并增加 learned-vs-GT light direction loss；
3. 降低或延后 light LR；
4. Per-light 在 baseline geometry 收敛后再启用，避免从 iteration 1 同时自由
   优化 geometry、normal、light 和 albedo。

其中第 1 项最适合验证 normal 退化究竟来自 light 估计误差还是 shading normal
符号不一致。

## 14. 棘手点与最终判断

本次检查中容易混淆的地方是 contact sheet normal 与 shader normal 并不是同一个
张量：

- contact sheet：取负后的 rasterizer camera-space normal；
- normal regularizer：rasterizer camera-facing world-space normal；
- per-light shading：未 camera-facing 的 world-space local `+z` normal。

因此，单独检查 `n` 和 `l` 是否都是 world-space 会得到“正确”，但仍不足以保证
训练一致；normal 的正负面语义同样必须一致。

最终判断：

- Lambertian ray 正负号：**PASS**
- Per-Gaussian normal/light 归一化：**PASS**
- Blender → internal camera 轴转换：**PASS**
- Shader 中 normal/light 坐标空间：**PASS**
- Raster normal map 逐像素单位化：**未执行，沿用 baseline alpha-weighted 行为**
- Photometric normal 与 rasterizer normal 定向一致性：**FAILED**
- Learned light 与真实 light 对齐：**FAILED**
- Per-light normal 视觉与 depth-normal 定量验收：**FAILED**

因此，在继续进行更高 light LR、更多 iteration 或其他 per-light sweep 前，应先
修复 normal 的双面定向一致性，并以固定真实 light 的小规模实验验证。

   normal 质量；它是必要的诊断修复，不是充分的质量修复。
2. 固定 GT light 将三帧平均误差从 `43.48°` 降到 `34.41°`，改善 `20.9%`，
   说明 learned light 的约 `34°` 方向误差确实是退化原因之一。
3. GT-light 仍比 baseline 高 `15.40°`，并在 t=59/119 出现条带状漂浮
   Gaussian；large separation 的底座大面积转为动态。因此剩余问题主要来自
   light/normal/albedo/geometry 联合分解歧义，以及简化 Lambertian 未建模 area
   light、距离衰减、阴影、间接光和高光。
4. 原始 SH baseline 仍是四组中 normal 和 separation 最好的版本。
